# Large external-vault exports outlive the poll activity's 60 s heartbeat timeout

**Found:** 2026-10-04, in the whole-branch review of `fix/vault-api-alignment`. Pre-existing: the timeout arrived in `06f6971c` (2026-05-03, a broad backend refactor), which undid the April fix that had removed the poll activity's heartbeat timeout after it killed a 237 MB download.

**Root cause:** both import workflows schedule the poll activity with `heartbeat_timeout=timedelta(seconds=60)` (`backend/src/cellar/infrastructure/temporal/workflows/cdd_vault_import.py:359`, `cdd_plate_import.py:300`). Once the export is finished, `poll_molecule_export` (`backend/src/cellar/infrastructure/temporal/activities/cdd_fetch.py`) heartbeats once before the download and once before `json.load`, and never during the download, the parse, or the chunk writes. A full-vault export (about 502K molecules, hundreds of MB) takes longer than 60 s in at least one of those steps.

**Impact:** Temporal times the attempt out and starts the next one while the first is still running. The new attempt deletes the old one's `raw_export.json.tmp` and downloads into a fresh one, and the old attempt's later rename can move the new attempt's half-written file to `raw_export.json`. Attempts then fail on `JSONDecodeError` or `FileNotFoundError`. Because the parse and chunking step alone can also run past 60 s, a full import can use up all 10 attempts and fail. Small imports (the "max molecules" cap, single plates) are unaffected.

**Fix direction:** heartbeat from inside the long steps instead of dropping the timeout. Give `CddVaultClient.stream_export_to_file` an optional per-chunk callback that the activity sets to `activity.heartbeat` (the SDK throttles the actual sends), and heartbeat between chunk-file writes. Only workflows started after the change get it, because activity options are fixed when the activity is scheduled. Test it with an `ActivityEnvironment` run whose fake download yields several chunks and assert the heartbeats.
