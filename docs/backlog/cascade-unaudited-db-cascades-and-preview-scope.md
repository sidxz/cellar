# Cascade: unaudited DB cascades, preview's missing workspace check, and the plan-apply race

**Found:** 2026-09-15, final review of feat/force-delete-id-references (spec docs/superpowers/specs/2026-09-15-force-delete-id-references-design.md).

**Root cause 1 — rows removed by a DB `ON DELETE CASCADE` get no audit snapshot.** `CascadeRunner.execute` (`backend/src/cellar/infrastructure/cascade/cascade_runner.py:300-342`) snapshots and deletes only the rows its own rule walk finds (`_snapshot_deletes`, :358-372, and the `DELETE` loop over `plan.deletes`). A row a Postgres `ON DELETE CASCADE` clause removes as a side effect of one of those statements is never selected, so it gets no `AuditEntry`, DELETE or otherwise — the row is simply gone with no trail. Concretely (see the `IGNORED_FKS` rationale comments in `backend/tests/unit/cascade/test_fk_coverage.py`):
- a molecule force delete's `DELETE FROM molecule_identifiers ...` DB-cascades to `batch_identifiers.derived_from_molecule_identifier_id` (`test_fk_coverage.py:256-267`);
- a protocol or run force delete's own `DELETE` DB-cascades the tag link tables (`protocol_tags.protocol_id` etc., `test_fk_coverage.py:282-301`), the owner side of the target link tables (`protocol_targets.protocol_id` / `run_targets.run_id`, `test_fk_coverage.py:269-280`), and `run_collections.run_id` (`ondelete="CASCADE"`, `backend/src/cellar/infrastructure/persistence/sqlalchemy/screening_assay/models.py:117`).

**Root cause 2 — preview never checks the root exists in the caller's workspace.** `CascadePreview.__call__` (`backend/src/cellar/application/admin/cascade_preview.py:33-52`) checks `require_same_workspace(auth, input.workspace_id)` — the caller's own claim — but never that `input.entity_id` actually names a row in that workspace. `CascadeRunner.preview` → `_build_node_for_root` → `_fetch_label` (`cascade_runner.py:198-205`) scopes the root lookup by workspace and returns `None` on a miss, but the walk continues regardless: children are correctly workspace-scoped where their table has `workspace_id`, but a table without one (readout/condition definitions) has nothing to scope by, so a foreign id can still walk into it and return its names. `CascadeDelete`'s execute path is not exposed the same way, because it requires the admin to type the entity's exact display name to confirm — a foreign id's blank label can't match. Risk is low: the endpoint is admin-only and ids are unguessable, so this is a defense-in-depth gap, not an active hole.

**Root cause 3 — plan → apply race (predates this branch).** `CascadeRunner.execute` calls `plan()` then applies it in the same transaction, under the default READ COMMITTED isolation. A new row referencing the root, committed by a concurrent transaction between `plan()`'s reads and the `DELETE`s, is invisible to `plan()` and is not blocked, nulled or removed — it just ends up dangling. The pre-branch runner had the identical shape (collect ids, then act), so this is not a regression.

**Fix direction:**
1. Either snapshot the DB-cascaded rows explicitly before deleting their FK-owning parent (one more `_snapshot_deletes`-style read per DB-cascade edge), or accept the gap and say so in the spec.
2. Have `CascadePreview` (or `CascadeService.preview`) fetch and check the root row's `workspace_id` up front, the same way `CascadeDelete`'s typed-name confirmation effectively does, and return `NotFoundError` on a miss.
3. `SELECT ... FOR UPDATE` on the root row at the start of `execute` (after `plan()`, before the writes) would narrow the race without a full serializable transaction; a real fix needs the writes to re-check what `plan()` assumed, or a stricter isolation level for the whole operation.
